Proving the link between the two chips

A test procedure for the new inter-chip communication module. Forty minutes on a bench, two boards and a USB cable — and at the end of it you know the transport is not the thing that is wrong.

STM32F407ZGT6 ↔ ESP32-S3 Protocol v2.0 Implements P2 + P4 of UNIVERSAL_PROCESS_IMAGE.html

01What was built, and where it lives

The connection between the two chips is now a module with a published contract, not a handler bolted to whatever was convenient. Three files on each side, one header shared between them, and a single point at which the rest of the firmware plugs in.

The shape matters more than the code. The industrial half owns the field buses and writes everything it learns into a RAM process image. The network half asks for a slice of that image and publishes it. Neither one waits for the other, and neither one knows anything about the other's world — the link carries bytes and quality flags, never Modbus register numbers and never MQTT topics. That is what lets three different clouds and five different field buses be added later without either side learning a new protocol.

FileSideRole
shared/gw_model.hbothThe wire contract. Framing, opcodes, status codes, region ids, quality codes, payload structs. Compiled by both projects through a two-line shim, so there is exactly one copy.
Core/Inc/gw_link_cfg.hSTM32Every local tunable: buffer sizes, slots per region, the master GW_LINK_ENABLE switch.
Core/Src/gw_image.cSTM32The process image. Regions, slots, quality, timestamps, bounds checks. Drivers write it; the link reads it.
Core/Src/gw_link.cSTM32The protocol engine. Parses a request, answers it from the image, never blocks, never calls a field bus.
Core/Src/gw_link_port.cSTM32The only file that knows about a UART. Circular RX DMA, TX DMA, and a health check. Move to another port or to SPI by rewriting this one file.
include/stm_link_v2.hESP32The client. One synchronous, retried, mutex-guarded transaction per call.
src/linkv2_test_main.cppESP32The bring-up console this document drives. Its own firmware, built by the linkv2 environment.

What the rest of the firmware plugs into

A future driver — the RS-485 scanner, local IO, CAN — never touches the link. It writes slots, and the link serves them. That is the entire integration surface: 

/* an RS-485 scanner, when it lands (phase P3) */
GwImage_SetU32(GW_REGION_MB_RTU, slot, value, GW_Q_GOOD);
GwImage_SetQuality(GW_REGION_MB_RTU, slot, GW_Q_COMM_FAIL);  /* slave stopped answering */

/* the superloop in main.c */
while (1) {
    GwLink_Step();    /* parse a request, answer it from the image */
    GwImage_Step();   /* uptime, staleness ageing, demo slots        */
    /* RtuScan_Step(); LocalIo_Step(); Can_Step(); ... all state machines */
}
Why the demo generator exists

With GW_IMAGE_DEMO 1 the STM32 animates six slots of the Modbus RTU region: a counter, a triangle wave, a float, a toggling bool, one slot left at COMM_FAIL and one never written at all. It means the link can be proven end to end, quality codes included, before a single RS-485 device is wired. Set it to 0 the day the real scanner owns those slots — two writers on one slot is the one rule this architecture cannot bend.

02The bench

Two boards, three wires and two USB cables. No RS-485 device, no WiFi, no certificates, no cloud account. Everything in this document runs on that.

ESP32-S3STM32F407Note
GPIO18 — PIN_STM_RX←PB10 — USART3_TXCrossed. RX to TX.
GPIO17 — PIN_STM_TX→PB11 — USART3_RXCrossed the other way.
GND—GNDMandatory, and keep it short. Most "random CRC errors" are this wire.
GPIO43 / 44——UART0, the debug console. This is where the test output appears. Never log to Serial1.

115200 8N1, which must match huart3.Init.BaudRate in the STM32's main.c and STM_LINK_BAUD in the ESP32's config.h. Raise both together once the link is proven, not before.

If the two boards have separate supplies

Common ground first, always. If the industrial side is mains-referenced, put a two-channel digital isolator in the data lines — being cheap to isolate is one of the reasons this link is a UART and not SPI. A missing or long ground shows up as intermittent CRC errors that look exactly like a firmware bug.

03Flash both halves

01

Let STM32CubeIDE see the new files

Four new source files landed in Core/Src and five headers in Core/Inc. CubeIDE builds from a generated Debug/Core/Src/subdir.mk, which it only rewrites when it re-scans the project. Open the project, press F5 on it in the Project Explorer, then Project → Clean.

Symptom if you skip this: undefined references to GwLink_Init and GwImage_Init at link time, even though the files are plainly there.

02

Build and flash the STM32

Build Debug and flash over ST-LINK with the existing ModbusRTU_AWS Debug.launch. Nothing about the .ioc changed, so no CubeMX regeneration is needed — and all application code sits inside USER CODE markers, so a regeneration would not destroy it either.

GW_LINK_ENABLE defaults to 1, which gives USART3 to the new module. The old 0xAA/0xBB handler is still compiled and one #define away; the two cannot share the port, because v1 polls it one byte at a time from the main loop.

03

Check two variables before you unplug the debugger

gwImageOk and gwLinkOk are globals in main.c precisely so they can be watched. Live expressions are already enabled in the launch configuration. Both must be true.

gwImageOk == false means the configured regions do not fit GW_IMAGE_BYTES, or the image landed somewhere DMA cannot reach. gwLinkOk == false means USART3 has no DMA stream linked — check the .ioc.

04

Build and flash the ESP32

pio run -e linkv2 -t upload -t monitor

No secrets.h, no certificates, no libraries to download. The environment compiles the test console, the v2 client and the CRC, and nothing else — if it fails to build, nothing about the cloud is involved.

05

Watch it run itself

The console runs the whole suite once at boot, so plugging the board in is the test. After that it waits for a key: a runs everything again, ? lists the menu, l opens a live view of the image.

04The wire format, on one screen

Worth twenty seconds before you read any traces. Everything is little endian, including the CRC. The header is self-describing: frame length is always header + LEN + 2, for every opcode, with no special cases. That single property is why one parser handles every frame and why a corrupted byte can never leave either side unable to resynchronise.

A complete transaction, byte for byte. This is an ECHO of the two characters Hi, and it is a frame you can paste into a terminal yourself — see section 08. 

out  A5 01 7F 00 00 00 02 00 48 69 DB F7
     ^  ^  ^  ^  ^---^ ^---^ ^---^ ^---^
     |  |  |  |  off=0 len=2 "Hi"  CRC
     |  |  |  region 0 (unused by ECHO)
     |  |  opcode 0x7F = ECHO
     |  sequence 0x01
     start of request

in   5A 01 00 00 02 00 48 69 22 1E
     ^  ^  ^  ^  ^---^ ^---^ ^---^
     |  |  |  |  len=2 "Hi"  CRC
     |  |  status 0x00 = OK
     |  sequence echoed
     start of response

Reading the round-trip numbers

A 64-byte echo moves 146 bytes over the wire, which is 12.7 ms of pure transmission at 115200 baud. Measured 13.0 ms means the STM32's own handling cost about 300 µs — it answered essentially immediately. That is the claim the process image makes, and it is the number to compare against v1, where the same shape of request could take 1.6 seconds because it ran a live Modbus transaction inside the reply.

Everything above is wire time, so raising the baud is what makes it faster. At 921600 the same echo is 1.6 ms.

06What each test actually proves

If one fails, this is the column that tells you where to look. They are ordered so that a failure early makes the later results meaningless — fix them in order.

TestProvesIf it fails
T1 ECHO Wiring, baud, DMA on both sides, framing, CRC. Nothing above the transport is involved. Stop here. Nothing below means anything until this passes at all five sizes. If small sizes pass and 1024 fails, suspect the receive buffer sizes rather than the cable.
T2 SYNC Both chips agree on the protocol version, and the STM32's clock is running. A version mismatch means one chip was flashed with an older shared/gw_model.h. Frozen uptime means SysTick is dead — the link would look perfectly healthy.
T3 RD_META The ESP32 can discover the image layout instead of hardcoding it, and the block arithmetic is self-consistent. Offsets that fail the consistency check mean the region table and the layout code disagree. Every later read would be shifted by a few bytes and return plausible nonsense.
T4 SYS region A real region read works, and the STM32's own counters confirm it is seeing the same traffic you think you sent. Compare rx here with requests in the client statistics. A gap is bytes being lost; look at dropped and the fault bits.
T5 Slots The full path: a driver wrote a slot, the image stamped and graded it, the bytes arrived here meaning the same thing. Quality codes included. If slot 0 does not advance between two reads, the superloop is stalled — something is blocking. That is a value that looks fine and is not being refreshed, which is exactly what v1 could not report.
T6 WR_REGION The network half can fill the region it owns, and only that one. A NOT_WRITABLE here means the MB_TCP region lost its GW_REGF_WRITABLE flag in the region table.
T7 Errors Every refusal path, and that none of them wedges the parser. The duplicate-sequence check proves a retried write cannot apply twice. The last check — "link still healthy" — is the important one. If it fails, the parser can be jammed by a malformed frame, which is the defect v1 carried a client-side resync hack to work around.
T8 Soak It keeps working. Two hundred transactions with no retries is the difference between "it worked once" and "it works". Occasional timeouts with a clean cable point at the STM32 superloop stalling. Occasional CRC errors point at grounding or cable length.

Quality codes you will see in T5

Quality is the reason this rewrite exists. In the old link a Modbus timeout was answered with STATUS_OK and stale bytes, so the cloud was told bad data was good — a wrong number with a plausible shape, and nothing anywhere to detect it. Now every value carries its own verdict.

CodeNameMeansPublish it?
0unknownNever read since boot. Not the same as "read successfully as zero".no
1goodFresh and trustworthy.yes
2staleThe last read succeeded, but longer ago than the staleness window.with the flag
3commFailThe device stopped answering. The last known value is still visible, which is useful to a human and misleading to a chart.with the flag
4–7exception, configErr, overrange, disabledDefined for the drivers that land in later phases.with the flag

07Testing the STM32 with no ESP32 at all

Useful when you suspect the ESP32, when you have only one board, or when you want to see raw bytes rather than a client's interpretation of them. Any USB-to-serial adapter at 115200 8N1 will do: adapter TX to PB11, adapter RX to PB10, ground to ground. Use a terminal that sends and shows hex — RealTerm, Docklight, or the HEX mode of most serial monitors.

Every frame below is complete and correct, CRC included. Send the bytes, read the reply.

The last two are the quickest confidence check in this document: two frames, two known replies, and they prove the parser, the dispatcher and the CRC in both directions. The quality row is the most informative — 01 01 01 01 03 00 00 00 is four good slots, one in comm-fail, and three never written, which is the demo generator doing exactly what it says.

Making your own frames

CRC-16/MODBUS, polynomial 0xA001 reflected, init 0xFFFF, no final xor, low byte transmitted first — the same CRC the RS-485 side already uses, deliberately, so there is no second implementation to get wrong. Its check value over ASCII "123456789" is 0x4B37, and both firmwares verify that at boot.

08When it fails

SymptomMost likely causeWhat to do
Every test times out. STM32 rx counter stays at 0. Nothing is arriving. TX and RX not crossed, no common ground, or the STM32 is not running this firmware. Swap the two data wires — it is the single most common cause. Then check gwLinkOk on the debugger.
STM32 rx counter climbs, but the ESP32 sees nothing. Requests arrive, replies do not. STM32 TX (PB10) is not reaching the ESP32 RX pin. Scope or probe PB10 during a test. If it is transmitting, the fault is between PB10 and GPIO18.
Undefined reference to GwLink_Init when linking the STM32. CubeIDE has not re-scanned the project, so the new files are missing from subdir.mk. F5 on the project, then Project → Clean. Step 01 of section 03.
Small echoes pass, 1024-byte echo times out. A buffer smaller than the largest frame somewhere in the chain. Check STMV2_RX_BUFFER (ESP32) and GW_LINK_RX_DMA_BYTES (STM32) against GW_MAX_PAYLOAD.
Occasional CRC errors, no pattern. Electrical. Long or missing ground, unshielded jumpers next to a switching supply, or a floating line. Shorten the ground wire first. The STM32's dropped counter rising in bursts alongside CRC errors confirms noise; steadily rising with no CRC errors instead means a baud mismatch.
Everything works, but GW_FAULT_LINK_OVERRUN is set in the SYS fault bits. The STM32 superloop stalled long enough for the DMA ring to lap, or the HAL aborted the receive after an overrun and the module restarted it. Not fatal — the link recovered. But find what blocked: at 115200 baud this needs 133 ms of unserviced loop. Almost always a blocking call that should be a state machine.
T5 slot 0 does not change between reads. GwImage_Step() is not being called, or GW_IMAGE_DEMO is 0. Check the superloop in main.c. A frozen value with GOOD quality is the exact failure mode this architecture exists to make impossible.
Client reports SEQ errors during the soak. Replies arriving after their request timed out — the STM32 is slower than STMV2_RSP_TIMEOUT_MS some of the time. Working as designed: the stale reply is dropped rather than mistaken for the next answer. Raise the timeout or find the stall.
Protocol version mismatch reported by T2. The two chips were built from different copies of shared/gw_model.h. Rebuild and reflash both. There is only one copy in the repository; if a project has its own, delete it.

09Pass criteria, and what comes next

Done when

39 passed, 0 failed, and a soak of 200 transactions with zero retries and zero errors. Record the average round trip — it is the baseline every later change is measured against, and the number that will tell you whether the RS-485 scanner, once it lands, is stealing time from the link.

What this unlocks, in order. Each step leaves a gateway that still works; none of them needs a switchover.

Immediately next

The three cloud back ends

The link is deliberately cloud-agnostic: it hands over raw values, timestamps and quality codes, and knows nothing about AWS IoT, ThingsBoard or a plain MQTT broker. A back-end interface over the process image, with the broker, port, credentials and topic shape chosen from configuration, is the next module — and it does not touch anything tested here.

Then, on the STM32

The non-blocking RS-485 scanner

Phase P3: convert modbusMaster.c from a blocking HAL_MAX_DELAY transaction into a state machine, group registers into block reads, and let it fill the MB_RTU region at its own pace. Turn GW_IMAGE_DEMO off in the same commit, and re-run this document's suite — the numbers should not move.

After that the queued write path and the event ring (WR_CHANNEL, RD_ACK, RD_EVENTS, and the STM_EVENT GPIO that lets an alarm bypass the poll interval), then configuration in flash and the PC commissioning tool. Every one of those is an addition to this module rather than a change to it, which is the real test of whether the interface above was drawn in the right place.
