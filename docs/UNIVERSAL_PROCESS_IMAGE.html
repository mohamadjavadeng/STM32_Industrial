STM32F407 + ESP32-S3 gateway · architecture plan

One memory image, many buses

Your two ideas — memory areas per protocol, and fixed arrays of structs — are not two options. They are the two halves of one design, and every real PLC ships both. This is what each half does, and the order to build them in.

ModbusRTU_AWS · IoTHandler Extends docs/GATEWAY_ARCHITECTURE.md §4

01The two layers

The structs describe where a value comes from. They almost never change, and they stay in flash. The memory regions hold what the value is right now. They change every scan, and only they cross the link.

Your idea B · the structs

Configuration. Flash. Rarely changes.

Slave ID, register number, register class, data type, scan rate, scaling. The ESP32 never sees any of it.

Your idea A · the memory areas

Process image. RAM. Changes constantly.

Value, quality, timestamp. Nothing else. This is the only thing that travels over the UART.

02One value, end to end

Follow a single pressure reading from the RS-485 slave to the cloud. Notice where the Modbus address stops existing.

03Why the image, not a proxy

Today the link is a pass-through: an ESP32 request triggers a live Modbus transaction and waits for it. That is the source of most of your known bugs.

The second reason: grouping

Once the scanner is free-running it can read registers in blocks instead of one at a time. At 9600 baud that is the difference between a scan you can use and one you cannot.

Consequence for the design

The scanner must iterate request groups, not channels. Build those groups when the config is committed: sort by (port, slaveId, fc, address), merge runs of up to 125 registers, store as a second table. The runtime never sorts anything.

04The memory map

One flat byte array in SRAM, cut into a region per protocol — exactly your idea. 8 KB total. Sizes are decided at commit time, not hardcoded.

SYS LOCAL_IO MB_RTU MB_TCP CAN SERIAL VIRTUAL EVENTS

Inside one region

Three parallel blocks, not an array of structs. The ESP32 almost always wants all values or all qualities, and a contiguous block is one memcpy.

F407 gotcha

Put the image in SRAM1 at 0x20000000, never in the 64 KB CCM at 0x10000000. CCM is not reachable by DMA on the STM32F4, and serving the link from DMA is the whole point. Put the stack and the config copy in CCM instead.

No mutex needed

On Cortex-M4 an aligned 32-bit store is atomic, so a reader can never catch half a value. It can catch slot 5 being 3 ms newer than slot 4 — which is what a process image is, and what the timestamp block is for. Add a per-region seq counter so a consumer that needs a consistent set can read seq, read the block, read seq again, retry on mismatch. No critical sections, no blocked scan.

05Quality — the bug this kills

Today a failed Modbus read is answered with STATUS_OK and stale bytes (quirk Q5). The cloud is told bad data is good. Make quality a real value that travels with every slot.

The interlock you must not skip

Once the PC tool can reassign slots, "slot 5 of region 0x02" stops meaning the same thing forever. If the ESP32 publishes with an older map than the STM32 is filling, every tag is silently mislabelled — pressure reported as temperature, and nothing anywhere errors.

Store a CRC32 + version with the config, return it in SYS and in every RD_META, and have the ESP32 refuse to publish on mismatch. Cheap now. Impossible to retrofit after the first field incident.

06The link protocol, version 2

Your sketch SOF | CMD | RD/WR | data | CRC | EOF is the right shape. Four changes, each paying for a class of bug you already have.

Drop the EOF byte

In a binary protocol no byte can be reserved as a terminator, because payload may contain it. LEN + CRC is the frame boundary. EOF costs a byte and buys false confidence.

Add explicit 16-bit LEN

Today the STM32 infers length from the command (6 + (cmd==WRITE ? count : 0) + 2). That inference is the root of the byte-versus-register confusion in Q2 and Q3. One parser, one length field.

Add SEQ, echoed back

Kills the whole desync family: Q4's ghost frame, and the subtle case where a late reply to a timed-out request is eaten as the answer to the next one. The ESP32's resync() hack disappears.

Make STATUS a result code

Not "I understood your frame" but "here is what happened": OK, BAD_CRC, BAD_CMD, BAD_REGION, RANGE, BUSY, CFG_MISMATCH, NOT_WRITABLE, QUEUE_FULL, FLASH_ERR.

Keep CRC-16/MODBUS (poly 0xA001, init 0xFFFF, low byte first). It is already correct on both sides and reusing it means no new test surface. Cap payload at 1024 B and size the STM32 RX buffer at 2 KB — today's 64-byte buffer with no bounds check (Q8) is a live overflow and must not survive the refactor.

Migration — no big-bang switch

Run both protocols during the change. 0xAA enters the v1 parser, 0xA5 enters v2, and v1 is re-implemented to answer from the image instead of hitting RS-485. The ESP32 tries RD_META at boot and falls back to v1 if there is no reply. Once it runs on v2 only, delete v1 and set STM_FW_QUIRKS 0.

Writes never run inline

07Drivers

7.1  The channel struct

One shared pool of 512 channels, not fixed 100 per protocol — a gateway wired to a single 300-point energy meter should not be stuck at 100 while 400 CAN slots sit empty. Same RAM, far more useful.

And a CAN address shares nothing with a Modbus address, so do not force them into common fields. Use a union.

7.2  RS-485: a state machine, never a blocking call

7.3  CAN is not request/response

Nothing polls CAN — frames arrive when the bus decides. The driver is an interrupt handler with a lookup from canId to the signals that frame carries, each extracted by (startBit, bitLen, byteOrder, signed). That is exactly the DBC model, so your PC tool can import DBC files later without a format change. Quality here comes from a per-message receive timeout, and scanMs = 0 marks the channel event-driven.

Two bxCAN peripherals on the F407, 14 filter banks each. Allocate filters at commit from the distinct IDs in the table; fall back to mask acceptance plus software filtering when there are more IDs than banks.

7.4  Modbus TCP — decide where the master runs

Option A · on the ESP32

Recommended for v1.

The ESP32 already has lwIP. It polls TCP devices and pushes results into region 0x03 with WR_REGION. No new stack on the STM32, and the data model stays universal because the image is still the single destination.

The catch: if the ESP32 reboots, region 0x03 freezes holding plausible values. Add a per-region write watchdog on the STM32 that forces the whole region to COMM_FAIL after a timeout — otherwise you have recreated Q5 in a new place.

Option B · on the STM32

Only if you need it.

The F407ZG has an Ethernet MAC but needs an external PHY (LAN8720 or similar) plus lwIP on the industrial half. Choose this when the plant network is isolated from the WiFi network, or when TCP devices must keep being polled with the radio half dead.

It roughly doubles the STM32 firmware surface, which cuts against the "small enough to review, stable for years" argument for splitting the chips at all.

7.5  The rest, and the loop that runs them

  • Local IO is the easiest driver and the best one to write first — no bus, no timeouts, and it proves the whole config → image → link path. The unused GPIOs in main.h (PC4, PD12–PD15) plus ADC channels are enough.
  • Serial stays narrow in v1: fixed-offset binary frames on a configured port. Vendor ASCII protocols want a small scripting engine, which is a project of its own — defer it rather than half-build it.
  • Virtual channels read other slots and write their own: totalizers, conversions, alarm flags. Evaluate them last each pass, and forbid virtual-to-virtual chains in v1 so evaluation order cannot matter.
  • No RTOS. Keep the superloop and make every driver a state machine. An RTOS costs you the "small and reviewable" property the two-chip split was for.

While you are in there, wire STM_EVENT (STM32 → ESP32). The ESP32 already supports it through PIN_STM_EVENT; the STM32 has never driven it. It buys millisecond alarm latency without polling fast, and it is the natural signal for "an ack is ready" and "the event ring is not empty".

08The configuration tool

The PC project file is the single source of truth, and it generates both halves. That is where the design pays off.

ArtifactGoes toContains
project.jsonthe toolDevices, channels, names, units, comments. Version-controlled, diffable, readable.
config.binSTM32 flashHeader + region descriptors + packed ChannelDef array + precomputed request groups + CRC32.
tag_map.jsonESP32tagId → name, unit, region, slot, publish policy, MQTT topic. Stamped with the same CRC32.

Both outputs carry the identical CRC, so a mismatched pair is detectable instead of silently wrong. Ship tag_map.json to the ESP32 over MQTT or its own serial port and keep it in NVS — that removes the recompile step from commissioning entirely.

8.1  What makes it usable

  • A device profile library. One JSON per device model — "Schneider PM5560", "Delta VFD-M" — holding its register map. The engineer picks a device and a slave ID, not forty register numbers. This is the single biggest difference between a tool people use and a tool people avoid, and profiles accumulate across projects.
  • CSV import/export for the long tail, so bulk edits happen in a spreadsheet.
  • A feasibility check at commit. Estimated scan time per bus versus requested rates, region capacity versus channel count, duplicate slots. Refuse to build a config that cannot meet its own timing.
  • A live pane. Read the image now: value, quality and age per channel, plus a force-write button. Commissioning without this means guessing.

Qt 6 fits well here — table editing, device tree and live view are all things Qt Widgets does properly, and it deploys to Windows with no runtime install.

8.2  Download, and why two flash slots

On commit: stop the scanners, rebuild region descriptors and request groups, set every quality to UNKNOWN, bump the config version, restart. A reboot is an acceptable v1 shortcut — and an honest one.

09Build order

Every phase leaves a gateway that still works. Nothing here needs a switchover — which matters, because you have hardware on a bench and a cloud path that already runs.

P1

Freeze and measure

Tag the current firmware. Add a .gitignore for Debug/ and .metadata/ so real diffs stop drowning in build churn. Record today's link round-trip, scan time per tag, and behaviour with one slave unplugged.

Done when you have baseline numbers to compare against.

P2

Shared model header

Create shared/gw_model.h — types, region IDs, command codes, status codes. Include it from both projects. No behaviour change at all.

Done when ModbusRTU_AWS and both PlatformIO environments compile with it.

P3

Process image + non-blocking RTU scanner

The heart of the work. Add the image and region descriptors, compile the channel table in as a constant for now, convert modbusMaster.c to the state machine, add request grouping. Re-implement the existing 0xAA handlers to answer from the image so the ESP32 keeps working unchanged.

Done when link round-trip is under 5 ms and unplugging a slave changes only that tag's quality.

P4

Link v2 + DMA

USART3 to DMA with IDLE-line detection — already configured in the .ioc, never used. Add the 0xA5 parser beside 0xAA, and a StmLinkV2 on the ESP32 that negotiates with RD_META. Then delete v1.

Done when STM_FW_QUIRKS is 0 and STM_RSP_TIMEOUT_MS is 50.

P5

Config in flash

A/B slots, CRC32 verification, the CFG_* commands, group precomputation at commit, rollback on failure.

Done when you can change a slave ID from a test blob, push it, and pull power mid-download with nothing lost.

P6

PC tool v1

Project file, channel editor, device profiles, blob builder, download through the ESP32, live read pane, feasibility check.

Done when a device can be commissioned end to end without anyone opening an IDE.

P7

The other drivers

Local IO first (simplest, proves the path), then CAN, then Modbus TCP by whichever option you chose, then serial. Each is an isolated addition now — a driver, a region, a config record, profile entries in the tool.

P8

Writes, events, speed

Write queue and acks, the event ring, deadband publishing, STM_EVENT driven from the STM32, and raising both UARTs — the link to 460800 or 921600, RS-485 to 19200/38400 wherever field devices support it.

10Decisions you still owe

Fixed 100 channels per protocol, or one shared 512-channel pool?
Shared pool Same RAM, far more useful. Keep per-region caps in the config so one runaway protocol cannot starve another.
Where does the Modbus TCP master run?
ESP32 for v1 No new stack on the industrial half. Add the region write-watchdog on day one, not later.
4-byte fixed value slot, or a variable-width byte pool?
Fixed 4 bytes Covers bool through f32, makes the offset slot × 4, wastes 2 KB worst case on a 192 KB part. Add a byte pool only when a real string or blob channel appears.
Does control logic run on the STM32, or is it purely a gateway?
Answer before P3 If yes, the process image is also the control loop's I/O image and the write-ownership rule is mandatory. If no, the virtual region can stay small.
Real time on the STM32?
No RTC Stamp in milliseconds since boot; let the ESP32 convert to wall clock with the SYNC exchange. Keeps the industrial half free of time-source dependencies.
Config storage: internal flash or external EEPROM?
Internal flash, A/B 20 KB of config in a 1 MB part needs no extra hardware. Revisit only if config outgrows a sector, or you want it to survive a firmware reflash.

12The short version

Config in flash as structs. Values in RAM as regions. A link that only ever says "give me bytes from region R". A CRC binding both halves' idea of what those bytes mean.

Everything else — CAN, TCP, local IO, the PC tool — then becomes an addition rather than a redesign. That is the real test of whether the architecture is right.

Start at P3. It is the largest single step, it removes the worst live defect (bad data reported as good), and every phase after it is comparatively small.
