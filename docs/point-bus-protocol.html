Point Bus Protocol

A replacement for the 0xAA/0xBB link between the industrial and network halves of the gateway — designed so that adding CAN, Modbus TCP, custom serial or local IO costs a table entry, not a protocol revision.

Verdict keep the transport, replace the payload layer Status proposal, for review before implementation Supersedes esp32msghandler.c v1.2
01 Assessment

What survives contact with the bigger scope

Two of the three decisions in the current design hold up once CAN, Modbus TCP, serial devices and local IO enter the picture. The third does not.

The core problem

The current wire format encodes Modbus vocabulary directly: a request is register class plus 16-bit address. A CAN frame has no register class. An analog input has raw counts and a scale. A Modbus TCP slave needs a unit ID and an endpoint. A serial device returns a blob. None of those fit, so every new bus would force another opcode, another address convention, and another special case on both sides.

The fix is not a bigger opcode table. It is to stop describing how data is acquired on the link at all, and describe only which point is wanted. The STM32 owns a single flat namespace of numbered points; each point is bound internally to a Modbus register, a CAN signal, an ADC channel or a computed expression. The link never learns which.

Keep
  • UART as the transport — the bandwidth case for SPI still does not exist
  • ESP32 owns the request/response contract; STM32 answers
  • CRC-16/MODBUS — already verified identical on both sides, zero new code
  • One process image as the single source of truth, on the STM32
  • ESP32 keeps a mirror and publishes by exception
Change
  • Framing → delimiter-based, never trusts a length field
  • Envelope gains a transaction ID and a message type
  • Register class + address → point index
  • Quality becomes mandatory on the wire, not inferred
  • STM32 may push unsolicited events
  • Point metadata discovered at runtime, not duplicated in tag_map.cpp
  • STM32 gains an RTOS and one task per bus
Add
  • Session handshake and reboot detection
  • Wall-clock push from ESP32 → STM32
  • Change-only reads with a sequence watermark
  • Raw passthrough tunnel as an escape hatch
  • Bus diagnostics exposed as ordinary points
02 Failure analysis

Six ways the present protocol blocks the roadmap

Current design vs. the expanded requirement
LimitationWhereWhat breaks when you add a bus
Address model is Modbus-shaped type + u16 addr No way to name a CAN signal (29-bit ID + bit offset + length), a TCP slave (IP + unit + register), or an ADC channel with a scale.
No transaction ID header Responses are matched by arrival order alone. A late reply after a timeout is silently accepted as the answer to the next request.
Poll-only, no event path by design CAN is event-driven and digital inputs have edges. Polling drops transitions between scans; the fastest safe scan is bounded by the slowest bus.
Length is inferred and trusted packetLen A corrupted count byte overruns the 64-byte receive buffer, and a truncated frame wedges the parser with no timeout.
Status does not carry data validity STATUS_OK integrity A failed field read still answers OK with stale bytes. With one bus this is a bug; with five it is unmanageable.
Field access inside the request path handler Each request triggers a live transaction, so link latency equals the worst field-bus latency. Five buses means five ways to stall the link.
Worth fixing first, independently of everything else

The validity row is a live data-integrity defect, not a design limitation: statusModbus is computed and then never transmitted, so a timed-out RS-485 read reaches the cloud as a plausible number. That one is worth patching in the current firmware before any of this lands.

03 Shape

One namespace, many drivers

Everything below the process image is a driver that fills points on its own schedule. Everything above it speaks only point indices. The link sits at the boundary and knows nothing about either side's internals.

04 Stack

Four layers, each replaceable alone

The layering is the point. If bulk throughput ever demands SPI, only L1 changes and every message above it is untouched.

Layer responsibilities
LLayerCarriesDecisions
0PhysicalBytes UART 8N1. 115200 during migration (matches today), then 921600. Optional RTS/CTS. Two side-band GPIOs. STM32 uses DMA + IDLE-line, so framing costs no CPU.
1FramingDelimited, checked frames COBS with a 0x00 terminator, then CRC-16/MODBUS inside. The delimiter cannot occur in payload, so resync after any corruption is one byte-scan and the parser can never wedge. No length field is ever trusted.
2EnvelopeType, correlation, result 8-byte header: version, message type, opcode, transaction ID, status, flags, payload length. Requests and events are distinguishable, so an event arriving mid-transaction is dispatched, not mistaken for a reply.
3OperationsPoints and sessions Opcodes over the point namespace only. New buses add points, never opcodes.

Why COBS rather than a sync word and a length

The wedge-on-truncation and buffer-overrun bugs in the current firmware are both consequences of trusting a length byte with no reliable frame boundary. Consistent Overhead Byte Stuffing removes the class of bug rather than patching instances: one byte of overhead per 254, a guaranteed-unique terminator, and no escape sequence that can expand a frame. Roughly thirty lines each side.

Envelope layout

byte 0ver:4 type:4ver = 1. type: 0 REQ, 1 RSP, 2 EVT, 3 NAK
byte 1opcodesee opcode table
bytes 2–3txnIdLE. Echoed in RSP. Event sequence number in EVT
byte 4status0 in REQ; result code in RSP/NAK
byte 5flagsbit0 MORE, bit1 URGENT, rest reserved
bytes 6–7payloadLenLE. Validated against the decoded frame length
bytes 8…npayloadOpcode-specific. Bounded by the maxFrameLen agreed in HELLO
last 2crc16CRC-16/MODBUS over header + payload, low byte first

Total fixed cost per frame: 8 header + 2 CRC + up to 3 COBS + 1 terminator ≈ 14 bytes, or 0.15 ms at 921600.

05 Data model

The point namespace

A point is a numbered, typed, quality-stamped value. The index range determines the type, which is what makes bulk transfers fixed-stride and therefore cheap. Signed and unsigned share a range and are distinguished by metadata.

Index space
RangeTypeCountTypical occupants
0x0000–0x0FFFBOOL4096Digital in/out, Modbus coils and discretes, CAN bits, computed flags
0x1000–0x1FFFU16 / I164096Modbus registers, raw ADC counts, 16-bit CAN signals
0x2000–0x27FFU32 / I322048Counters, totalizers, 32-bit CAN signals, energy
0x2800–0x2FFFF322048Scaled engineering values, PID setpoints
0x3000–0x30FFBLOB ≤32B256Serial device payloads, raw CAN frames, identity strings
0xFF00–0xFFFFmixed256nice Bus counters, uptime, task load — read exactly like any other point, so diagnostics reach the cloud with no special-casing

Quality travels with every value

One byte per numeric point in bulk reads; a packed validity bitmap for the BOOL range. This is the structural fix for the stale-data defect — the ESP32 stops inferring freshness from timestamps because the STM32 states it.

Metadata is discovered, not duplicated

Today the tag table exists on both chips and will drift. Instead the STM32 publishes it: HELLO returns a pointTableCrc, and GET_POINT_META streams name, type, unit, scale, access and owning bus. The ESP32 caches the result in NVS keyed by that CRC and re-fetches only when it changes.

Cost: about 24 bytes of metadata per point. A thousand points is 24 kB — 260 ms once per firmware version, then never again. The STM32 becomes the single place a point is defined.

Does allowing STM32-initiated frames break the master decision?

No, because the decision was never about who may transmit — a full-duplex UART has separate wires and no hardware master. It was about who owns the request/response contract, and the ESP32 still does. The STM32 gains only the right to emit responseless EVT frames. What this does require is that the ESP32's receive path becomes a permanently running frame reader that dispatches by message type, rather than the current blocking wait-for-my-reply loop. That is the largest single change on the ESP32 side.

Backpressure is explicit: the STM32 keeps a bounded event queue, coalesces to the newest value per point when it fills, and reports the drop count. The attention-line GPIO stays useful as a wake hint for a sleeping ESP32 and as a fallback if events are ever disabled.

Change-only reads, and why the watermark matters

The STM32 keeps a monotonic changeSeq, stamped onto each point as it updates. READ_CHANGED(sinceSeq) returns everything newer and the new watermark. Because the request names an absolute sequence rather than "since you last asked", a lost or retried response changes nothing — it is idempotent. If sinceSeq is too old to reconstruct, the answer is RESYNC_REQUIRED and the ESP32 falls back to a full read. A dirty-bit scheme would be simpler and would lose changes on exactly the retry the link is built to perform.

07 Budget

Does it fit in a UART?

At 921600 baud, 8N1, one byte costs 10.85 µs. The numbers decide the transport argument, so they are worth writing down.

A realistic steady-state mix — change-driven reads at 10 Hz, a full reconciliation snapshot every few seconds, events as they happen — lands under 10% link utilisation. The transport has an order of magnitude of headroom, which is why UART remains the right answer and SPI remains unnecessary.

The one case that does not fit

Passing raw CAN frames straight through consumes nearly half the link on a single busy 250 kbit/s bus, and a 500 kbit/s bus would exceed it outright. CAN must be decoded into points on the STM32, with raw pass-up reserved for unmapped IDs and rate-limited. If you later want full raw CAN logging to the cloud, that is the one requirement that would genuinely justify adding SPI alongside the UART.

08 STM32 side

Five buses need an RTOS

One cooperative main loop cannot service five independent scanners with different timing without every driver becoming a hand-written state machine. FreeRTOS is already available through CubeMX, and it produces an unexpected saving.

Why this is cheaper than it sounds

Under an RTOS the existing blocking Modbus master becomes acceptable exactly as written. HAL_UART_Transmit with HAL_MAX_DELAY and a one-second receive timeout only block their own task — which is precisely what a bus driver task should do. The rewrite you would otherwise need, turning that code into a non-blocking state machine, disappears.

Task layout
TaskPriorityResponsibility
linkhighestDMA + IDLE receive, COBS decode, dispatch, serialize replies. Never touches a field bus, so never blocks.
canhighbxCAN FIFO ISR into a queue, decode ID and bit-field to points, transmit. Highest field priority because CAN will not wait.
mbrtumediumRS-485 poll list, one blocking transaction at a time, DE control.
mbtcpmediumModbus TCP client and/or server sockets.
iomediumDigital input debounce, analog oversample and filter, output application.
seriallowCustom device state machines on the spare USARTs.
logiclowVirtual points, totalizers, alarm evaluation, deadband and event generation.

Concurrency and placement

  • Each driver owns disjoint point ranges, so there is exactly one writer per point. Readers need no coordination for single-point access.
  • For consistent multi-point snapshots, one mutex around the image is sufficient — copying 3 kB on a 168 MHz M4 holds it for under 10 µs. Reach for a seqlock only if measurement says so.
  • Put the process image in CCM RAM. It is 64 kB, CPU-only, unreachable by DMA — which is a perfect fit for a structure no peripheral touches, and it leaves main SRAM for DMA buffers and a TCP stack. A thousand points of runtime state is roughly 8 kB.
  • Static point metadata lives in flash, about 32 bytes per point. There is 1 MB.

Spare capacity

Four USARTs remain for the serial devices: USART2 on PD5/PD6, USART6 on PC6/PC7, UART4 on PC10/PC11, UART5 on PC12/PD2. Prefer these routings over the PA0–PA3 alternates, which collide with RMII if Ethernet goes native.

Where Modbus TCP should live

Two questions hide inside one: acquiring from TCP slaves, and serving to a SCADA or HMI. They have different answers.

OptionCostVerdict
A. W5500 on the existing SPI2, STM32 acquires One chip plus CS and INT. No TCP stack, 8 hardware sockets, minimal RAM. recommended Modbus TCP moves almost no data; hardware sockets are ample. SPI2 is already configured and currently unused.
B. LAN8720 PHY, native RMII, LwIP Nine pins, a 50 MHz clock, real RAM and flash, PC4/PC5 surrendered. Only if you need many sockets or genuine throughput. Otherwise it buys complexity.
C. Modbus TCP server on the ESP32, from its mirror Software only. also do this A local HMI polls the gateway over the network it is already on, and the data is already sitting in the mirror. Cheap and useful.
D. ESP32 acquires from TCP slaves Software only. avoid unless forced Makes the ESP32 a second source of truth and splits the process image across two chips. Justified only when the slaves are reachable solely over the ESP32's network.

Also required and easy to forget: a CAN transceiver per channel, 120 Ω termination at both physical ends of the bus, and a decision about whether the CAN ground is the same ground as RS-485.

11 Open

Decisions I need from you

Each of these changes something concrete in the spec above. My recommendation is given where I have one, but these are yours to make.

How many points, and what is the fastest thing on the list?

Sizes the index space, the metadata transfer and the poll strategy. A hundred points at 1 Hz and five thousand at 50 ms are different machines.

Why it matters If anything needs faster than about 50 ms end to end, it should be closed-loop on the STM32 and only reported upward — not round-tripped through the link.

Modbus TCP: acquiring, serving, or both? W5500 or native PHY?

Decides whether PC4/PC5 stay as GPIO and whether the STM32 needs a TCP stack at all.

Recommend W5500 on the existing SPI2 for acquisition, plus a Modbus TCP server on the ESP32 serving its mirror for any local HMI.

CAN: raw IDs, CANopen, or J1939?

Raw means you hand-write ID-to-point bindings. J1939 means PGN and SPN decoding plus transport-protocol reassembly. CANopen means SDO, PDO mapping and NMT state. The three differ by an order of magnitude in effort, and the choice shapes the point metadata.

Also needed Bus rate, roughly how many distinct IDs, and whether the gateway ever transmits or only listens.

Who owns alarm logic — STM32 or cloud?

On the STM32 it keeps working through a WAN outage and can act on outputs; in the cloud it is easier to change. These are not exclusive.

Recommend Safety and interlocks on the STM32, always. Reporting thresholds and notification rules in the cloud.

How much history must survive an internet outage?

Minutes fit in ESP32 RAM. Hours belong in its flash. Days need an SD card or external flash, and change the mirror into a proper historian with backfill on reconnect.

Galvanic isolation on the inter-chip link?

If the industrial side is mains-referenced, two isolator channels on the UART is the cheapest barrier in the system — and a strong argument against ever moving to SPI, which would need four or more and be speed-limited by propagation delay.

Is the point table compile-time or field-configurable?

Compile-time is far simpler and is the right start. Field-configurable means a schema, validated persistent storage, and a way to recover from a bad configuration — worth deferring to phase 6, but worth knowing now because it affects how metadata is stored.

Local display or HMI on the device?

If yes, it reads the process image directly on the STM32 and must keep working with the ESP32 absent — which reinforces keeping all data ownership on the industrial half.
